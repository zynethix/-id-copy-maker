# 失败用例排查

查清一次失败的原因，判定是产品缺陷还是脚本缺陷，写下依据，停下来报告。**不管是哪一种，改之前都先告诉用户、等确认**。

## 何时使用

- `test-run` 有用例失败。
- 同一用例时过时不过（不稳定）。

## 步骤

1. **复现**：单独跑失败的用例（Playwright：`npx playwright test <脚本文件> -g <用例名>`），确认能稳定复现；不能复现也要记下来，按不稳定处理。单独重跑的证据写进项目约定的临时证据位置，不进执行记录；重跑的命令和读数写进当轮批次记录。
   要判断是不是证据配置本身引起的，可以关掉 trace 再跑一次（`--trace off`）对照。
2. **看证据**：打开这次运行的报告，看失败用例的截图和 trace——失败那一步页面是什么样、之前的操作是否如预期、控制台和网络有无异常。
3. **对照用例与需求**：失败的断言对应用例里哪条期望、需求文档哪一条。
4. **判定**：
   - 产品缺陷：页面行为与需求或用例的期望不符，且用例本身没错。
   - 脚本缺陷：产品行为符合需求，是脚本的定位、等待、素材、阈值或断言写错了。
   - 用例缺陷：用例的期望与需求不符或已过时。
   - 配置缺陷：测试配置或证据配置（如开启 trace）带出的问题，产品与脚本逻辑都没错。
   - 不稳定：同样条件下时过时不过；查出时序、日期、环境上的原因，归到上面四类之一。
5. **写依据**：失败的用例与步骤、看到的现象（截图或 trace 位置）、对照的需求条目、判定结论与理由。写进当轮批次记录。
6. **报告并停下**：把依据和建议的改法报告给用户，等确认。

## 确认后去哪

- 产品缺陷：按项目的开发流程修改产品代码，修完用 `test-run` 回归。
- 脚本缺陷：回 `test-script-gen` 修脚本，再 `test-run`。
- 用例缺陷：回 `test-case-design` 改用例，再改脚本、再跑。
- 配置缺陷：改测试配置，或在脚本里按 `test-script-gen` 的口径逐条放过并写明原因，再跑。

## 不做

- 不加自动重试，不调宽阈值让它通过：那会把真问题藏起来。
- 不在没报告的情况下改产品代码或脚本。
- 不删除失败的用例。
